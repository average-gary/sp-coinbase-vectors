Silent payments in the coinbase

How a mining pool could pay its miners directly in the block reward without publishing who got paid — and the one change to BIP 352 that makes it possible.

G — a fixed point on the curve that everyone agrees on.
a lowercase — a private key (a secret number). A uppercase — its public key, where A = a·G.
You can compute A from a. You cannot go backwards.

01 The problem

A pool that pays each miner in the coinbase writes every payout address into the block, in public, forever. Anyone can see how many miners the pool has, what each one earns, and — by watching over time — how each one's hashrate changes.

The fix would be for each payout to go to a fresh address that only that miner can recognise. Not a list of addresses handed over in advance — a rule both sides can compute, so that the pool can pay a fresh address every block and the miner can still find it.

02 How silent payments normally do this

A miner publishes two public keys instead of an address, and keeps both secrets: a scan key for spotting payments and a spend key for spending them.

miner publishes: B_scan = b_scan·G B_spend = b_spend·G pool has: A = a·G

Both sides can now compute the same secret without ever sending it, because scalar multiplication doesn't care about the order you do it in:

pool computes: s = a·B_scan = a·(b_scan·G) miner computes: s = b_scan·A = b_scan·(a·G) same point

The pool turns that shared secret into a number, and uses it to nudge the miner's spend key sideways into a brand-new address:

t = hash(s) P = B_spend + t·G ← the pool pays this address

The miner computes the same t, so it recognises P in the block. And it can spend from it, because the matching private key is just as simple:

p = b_spend + t check: p·G = (b_spend + t)·G = B_spend + t·G = P ✓

Why two keys, not one. Finding the money needs b_scan. Spending it needs b_spend. So b_scan can sit on an always-on machine doing the searching, while b_spend stays offline. Someone who steals the scanning key learns what you were paid but cannot touch it.

One thing is still missing. If the pool pays the same miner twice using the same a, then s is the same, t is the same, and P is the same address twice — which defeats the whole point. So the pool mixes in something that never repeats. Normally that's the outpoint: a pointer to the specific coin being spent, which by consensus can only ever be spent once.

h = hash(outpoint, A) s = h·a·B_scan

03 Why this breaks in a coinbase

The coinbase is the transaction that creates the block reward. It's special: it doesn't spend anything. And that breaks the scheme in two separate places.

There's no A. Look again at what the miner needs: s = h·b_scan·A. In an ordinary transaction the miner gets A for free, because it's the public key of the coins being spent and it's right there in the transaction. A coinbase spends no coins, so there is no public key anywhere in it. The miner has nothing to do the maths with.

There's no unique outpoint. Every coinbase in history points at the same placeholder — all zeroes. Using it as the nonce would give every block the same h, so a pool paying a miner each block would pay the same address every time.

04 The variation: two changes

The second problem turns out not to be a problem at all. Since 2013 every block has been required to write its own height into the coinbase. It's unique, it's already there, and both sides know it.

h = hash(H, A_send) H = the block height

The first problem is the real one, and the fix is to stop reusing a spending key for this job. Give the pool a key whose only purpose is this calculation — call it a_send — and publish A_send so miners can use it.

pool computes: s = h·a_send·B_scan miner computes: s = h·b_scan·A_send same point t = hash(s) P = B_spend + t·G ← this block's address for this miner p = b_spend + t ← only the miner can compute this

That's the whole variation. Everything downstream is unchanged.

05 Why the extra key is the point

It looks like a workaround for a missing value. It's actually the more interesting half.

In ordinary silent payments, a is doing two unrelated jobs at once: it does this shared-secret calculation, and it's the key that spends the sender's money. Those jobs have opposite requirements. Money keys must be kept forever. A privacy key should be destroyed the moment it's been used.

a_send spends nothing. Nobody's coins depend on it. So the pool can throw it away once the block is paid.

To be clear about what that is and isn't: deletion can't be proven. Nobody outside the pool can check whether a key was really destroyed or just quietly filed away, and no protocol can make that verifiable. So this is not an auditable guarantee, and shouldn't be sold as one.

What changes is that throwing the key away becomes possible at all. Today the sender's key spends money, so it must be kept — there is no version of the pool that doesn't hold it. With a dedicated a_send, a pool that wants to keep nothing is able to, and a key that no longer exists can't leak, can't be stolen, and can't be handed over later. Unverifiable but available beats unavailable, and it's the pool's own risk it's reducing, so the incentive points the right way without anyone having to take it on trust.

And if it leaks anyway, no money moves. An attacker holding a_send can compute s, and therefore t, and therefore work out which outputs went to which miner. But spending needs

p = b_spend + t

and b_spend never left the miner. Losing this key costs privacy, never funds — exactly the trade the miner already gets from splitting scan from spend. The variation just hands the sender the same deal.

06 Where A_send comes from

Whatever A_send the pool is using has to reach the miners somehow — 32 bytes. There are a few places it can go, and they're not equally good.

Note that A_send does not have to change every block for the payouts to stay unlinkable — the block height is already mixed into the hash, so every block produces different addresses even from the same A_send. Replacing it is about limiting how much history a single leaked key would expose. That makes the replacement rate a dial, not a requirement.

Down the mining connection. A pool is already talking to every one of its miners, so it can simply send them the list of A_send values, one per upcoming block. This costs nothing on-chain and is the best option. The catch is that a pool could serve different lists to different miners to tell them apart, so the list needs to be published somewhere public rather than whispered to each miner privately.

In the coinbase's spare bytes. Every block already has a small scratch area at the start of the coinbase, and a second one attached to the segwit commitment. Either has room. One constraint: while searching for a block, a miner rapidly rewrites part of that scratch area (the extranonce) millions of times a second. A_send has to sit outside those bytes — if it moved, every attempt would change all the payout addresses.

That first scratch area holds 100 bytes, and the room is there. Checked against the Stratum V2 reference pool:

Two details in there matter. The height slot is 8 because that's the largest the protocol permits and the software reserves it whether or not it's used — today's block heights only need 4, but you can't spend the difference. And the key has to go in as the x coordinate only, 32 bytes: the 33-byte form with its redundant prefix byte needs 66 hex characters and overruns.

Better, all 100 bytes are already reserved by mining software whether or not anything uses them, and unused ones are not handed back to fee-paying transactions. So the space is pre-paid: putting A_send there costs nothing.

Not the pool's own fee output — and the reason is worth understanding. A taproot output already is a public key sitting in the block, so it looks like a free carrier. But for taproot, knowing the secret behind that visible key is exactly what lets you spend the output. So if the fee output were A_send, then a_send would be the key that spends the pool's fee — a key holding money, which can never be thrown away. We'd be back where we started. Visibility and spendability are the same property there.

Trying to be clever with the output's spending conditions doesn't rescue it either, and the reason generalises past taproot. Anything that lets a scanner read A_send off an output that holds money either grants a_send the power to move that money, or requires it to sign and so forbids ever deleting it. One or the other, every time. The rule that falls out: A_send must never appear in a script that controls money. Put it in data, not in a spending condition.

The neat part: it can replace the pool's name tag. Pools already write a short bit of text into that scratch area — "/Foundry USA/" and so on — to sign their blocks. Put A_send there instead, and it costs nothing extra, because it's taking a slot that was already spoken for.

The pool doesn't even lose its public identity. If its list of A_send values is published — which it has to be anyway — then "this block used entry number H from that pool's list" identifies it just as well as a text tag. Better, in fact: anyone can type someone else's name into a block, but a copied A_send is inert, since you can't derive a single payment from it without holding a_send. The cost is that block explorers lose a human-readable label.

Two practical notes. The tag lands in the part of the coinbase the pool fixes, before the extranonce — so the "must sit outside the rolled bytes" rule above isn't something an implementer has to remember, it's how the message is built. And the tag is a text field, so A_send has to be written as text rather than raw bytes — which is where the chart above comes from. Hex fits with nothing to spare; an address-style encoding leaves room.

The tempting shortcut doesn't work. Publishing one key and deriving the rest looks free, and the maths does line up — the miner really can compute this block's key from the first one:

a_H = a_0 + hash(H) pool's secret for block H A_H = A_0 + hash(H)·G miner computes this from A_0

But read the first line again. Anyone who ever learns a_0 can compute a_H for every block, past and future, and unmask every payout the pool ever made. The one property worth having is gone.

That's not a flaw in this particular formula — it's the general case. If the miner can derive the key from something already published, then so can anyone holding the original secret. Independent keys have to be independently published. There's no shortcut.

07 Run it

The whole mechanism, executing in your browser: one pool, one miner, one block. The pool derives a payout address and writes A_send into the coinbase; the miner reads it back out and finds the same address. No libraries — the curve arithmetic is about forty lines of BigInt, and the hashing is the browser's own SHA-256.

08 The same thing in Python

The section above is a rewrite of the mechanism in JavaScript. This runs the Python implementation itself — a real CPython compiled to WebAssembly, fetching the files served next to this page — over all the cases, including the ones that show what happens when a piece of the construction is removed.

The catch is that a Python interpreter has to be downloaded first: about 6 MB from a CDN. Nothing is fetched until you press the button, and if you would rather not, python3 run_tests.py runs it at a terminal instead — all eleven cases if you also have a clone of bitcoin/bips, and the same nine as here if you don't.

Nine of the eleven cases run here. The rest print SKIP: they compare against unmodified BIP 352 code, which a browser has no way to fetch — including the case showing that plain silent payments reject a coinbase outright.

One warning if this tempts you to reuse the Python. The curve arithmetic comes from secp256k1lab, a teaching implementation whose own README says it is insecure and trivially vulnerable to side-channel attacks. It is the right tool for test vectors and the wrong one for anything holding money.

09 What this does and doesn't buy

It hides the payouts from everyone reading the blockchain. Each miner sees its own payment and learns nothing about the others.

It does not hide anything from the pool. The pool computed the payouts, so it knows exactly who is owed what — that's unavoidable in a scheme where one party decides the amounts. What changes is that the pool no longer has to publish that knowledge, and can choose not to keep the key that would let anyone reconstruct it later — with the caveat from section 5 that nobody outside the pool can check whether it really did.

Not a specification, not reviewed, not implemented anywhere. Builds on BIP 352 (silent payments) and BIP 34 (block height in the coinbase). The change is that BIP 352 deliberately uses the sender's spending key for the shared secret, because that key is the only one a transaction reveals for free; a coinbase reveals none, so the key has to be supplied on purpose — and once you're supplying it anyway, it may as well be one that isn't holding money.
